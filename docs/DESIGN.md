# LingEye 的设计哲学

版本：1.0.2  
作者：guaidao2 & coolmoon

## 1. 从插件到独立 agent

LingEye 最早的想法来自 dsh-lingeye：把安全测试过程组织成可追溯的事实、证据、意图和攻击路径，而不是一段聊天记录。

dsh-lingeye 是插件形态，必须服从宿主的存储、会话和 UI 假设。独立版本 lingeyebot 不是把插件代码换一种语言重写，而是重新回答一个问题：

> 如果安全 agent 是一个长期运行、项目驱动、需要人和多个子代理协作的系统，它应该怎样组织状态和边界？

因此，lingeyebot 保留了 dsh-lingeye 的核心思想，但把运行形态改成了独立服务：

- Go 单二进制
- SQLite 持久化
- 内嵌 React Web UI
- 项目 → 多个任务/对话
- 模型通道可独立配置
- MCP / Skills / 子代理是基础能力
- 本地优先，单用户

## 2. 基本信念

### 证据优先，而不是话术优先

安全结论不是“模型说它存在”，而是：

- 观察到了什么
- 在哪个授权范围内
- 通过什么请求/命令/输入
- 证据在哪里
- 是否可复现

所以系统区分 `observed / inferred / assumed / negative`。`observed` 必须绑定证据；漏洞必须有可复现步骤；覆盖率按“有证据覆盖”计算，而不是“工具跑过”。

### 项目是上下文，不是一次对话

一次对话无法承载授权、范围、资产、历史发现和长期记忆。项目是：

- 授权与范围
- 资产与发现
- 共享黑板与项目记忆
- 多个任务/对话
- 可审计的执行历史

对话是项目里的一次工作，不是项目本身。

### 信念图谱，而不是线性日志

安全测试的本质是不断修正信念：

- 我以为什么是入口
- 我实际观察到了什么
- 哪条路径被证伪
- 哪个负面结果值得保留
- 哪个发现改变了攻击路径

图谱把目标、意图、事实、漏洞、证据和关系保存下来，允许失败路径和 negative fact 存在。它不是装饰，而是 agent 的决策上下文。

### 目标模式是可选能力

自主推进很强，但也很贵、很危险。所以目标模式默认关闭：

- 不启用：普通对话，不自动继续
- 启用：目标 + 验收条件；达成即停，未达成继续
- 默认不限制轮数/迭代；只有显式设置上限才会限制
- 随时停止/插话/继续

自主性默认交给用户控制：不设硬预算，用户随时可以停止；目标完成则停。只有用户显式设置上限时才会自动暂停。

### 模式是 doctrine，不是 prompt 拼盘

五种模式不是换一段提示词，而是不同的工作 Doctrine：

- 日常：安全伴侣、配置检查、安全开发
- BugBounty：SRC 漏洞挖掘
- 代码审计：白盒验证
- 红队：ATT&CK 行动框架
- CTF：以拿到 flag 为可判定目标

模式决定工具、角色、提示词、验收和停止条件。

### 子代理是分工，不是并发装饰

子代理不是“多开几个模型”。它用于把工作拆成可交付的角色：

- 情报收集
- 主动枚举
- 脆弱点建模
- 前渗透
- 后渗透
- 隐蔽
- worker

每个子代理有独立会话、任务状态、预算、inbox 和结果。实时输出属于子代理自己的任务详情；主对话只保留主代理输出。子代理完成后，结果进入任务详情，并作为一条**隐藏的上下文消息**回到主代理，而不是伪装成用户消息塞进聊天。

### 共享黑板由 agent 维护

黑板不是人类表单，也不是 UI 收藏夹。它是指挥官和子代理共享的工作记忆：

- 决策
- 事实
- 凭据
- 联系人
- 下一步

人类通过对话下达指令；agent 负责把可复用结论写到黑板上。

### 人在回路可选，但审计不能省

默认自动执行，减少打扰；需要时可以开启审批。但无论哪种模式：

- 工具调用有审计
- 破坏性动作有硬边界
- 隐蔽员不能删除审计/证据
- 删除项目需要明确确认

## 3. 独立 agent 的架构选择

### 单二进制 + SQLite

安全工具经常要在隔离环境、笔记本、跳板机或靶场里运行。单二进制、纯 Go SQLite、内嵌 UI 减少了部署摩擦。

### 项目 → 任务 → 会话

- 项目：授权、范围、资产、发现、黑板、记忆
- 任务：一次有明确目的的工作
- 会话：模型消息与工具结果

任务可以独立停止、恢复、取消子代理；项目负责聚合。

### 服务端拥有状态，前端负责呈现

前端不保存“真相”。事件、任务、证据、图谱和报告都在服务端；前端订阅 SSE 并渲染。这样刷新页面不会丢失状态，也不依赖某个浏览器实例。

### 事件必须带归属

1.0.1 修复了一类典型问题：子代理的流式 delta 必须带 `taskId`，主对话只能消费主代理事件；子代理输出进入自己的任务详情。否则并发时会出现“子代理说话串到主代理”的假象。

### 模型通道是配置，不是硬编码

不同模型网关对 `max_tokens`、`max_completion_tokens`、`reasoning_effort`、`thinking` 的支持不同。每个通道独立配置协议、端点、模型、输出上限、上下文窗口和推理字段。

## 4. 不做什么

LingEye 不是：

- C2 框架
- 漏洞利用武器库
- 无授权的自动扫描器
- 多租户 SaaS
- 对所有目标都保证覆盖的“万能安全大脑”

它不承诺“发现所有漏洞”。它承诺的是：把已经做过的观察、证据、失败路径和结论组织成可复核的工作台。

## 5. 设计张力

- **自主 vs 控制**：默认不自动继续；目标模式显式开启；随时可停。
- **结构 vs 自由**：图谱和证据提供结构，模型仍可选择下一步。
- **速度 vs 可信**：没有证据的结论不进入 observed；报告必须能复核。
- **本地 vs 协作**：单用户本地优先；子代理共享项目上下文，但不把密钥/数据发到外部。
- **开源 vs 安全**：只发布使用手册和设计思想，不公开会直接降低实战效果的私有策略细节。

## 6. 1.0.1 的变化

- 主代理与子代理的流式事件按 `taskId` 隔离
- 子代理实时输出进入自己的任务详情
- 子代理回交报告作为隐藏上下文回到主代理，不再显示为主对话用户消息
- 增加公开使用手册与设计哲学
- 版本号统一为 1.0.1

## 7. 1.0.2 的变化

- 主代理的可见内容和思维链改为双路流式：`reasoning_content` / `thinking` 通过独立 delta 进入“思考中”卡片，最终消息仍持久化完整 reasoning。
- 最终 assistant 事件先 emit、再落库，避免刷新时短暂重复思考块。
- 子代理 reasoning 暂不进入任务详情，避免把任务详情变成第二套主对话。
- 版本号统一为 1.0.2。

## 8. 最后

LingEye 的目标不是让模型“更会说话”，而是让安全测试过程更接近工程：

**假设 → 实验 → 观察 → 证据 → 结论 → 复核。**

模型可以犯错；系统必须让错误可见、可回滚、可审计。
